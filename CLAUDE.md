## Project Overview

This is a **Diablo II loot filter generator** for the Project Diablo 2 (PD2) mod. It produces `.filter` files that control item visibility in-game. The output filters are auto-generated by a GitHub Actions CI/CD pipeline — **do not manually edit the output `.filter` files in the root directory**.

## Build System

Filters are built automatically by `.github/workflows/build-filters.yml` on every push to non-main branches. The workflow:

1. Reads/increments `version.txt` (repo root) and generates a version stamp
2. Runs `python builderfilter/build.py`, which assembles numbered segment files from `builderfilter/` subdirectories into each output filter
3. Produces the root `.filter` outputs plus per-group copies under `filtergroups/` by combining segments with different tag inclusions
4. Renders the filter preview images (`examples/render/*.png`) via `python builderreadme/render_readme_images.py`, then regenerates `README.md`, the group READMEs and `filtergroups/HIIM_STYLES.md` via `python builderreadme/create_readme.py` (fills version + filter data into the `builderreadme/` template)
5. Validates with `validate_filters.py`, then auto-commits and pushes the generated outputs

**To trigger a CI build:** push to any branch other than `main`. **To build locally:** `python builderfilter/build.py` (then `python validate_filters.py`).

## Architecture: builderfilter Tag System

Source filter segments live in `builderfilter/` subdirectories, organized by category (01-header through 09-footer). Files use **filename tags** to control which output filters include them:

- `[ALL]` — included in every filter
- `[ONLY=FilterName]` — included only in the named filter
- `[ALL-EXCEPT=FilterName+OtherFilter]` — excluded from listed filters
- `[CRAFTING-ALL]` / `[LLD-ALL]` — shorthand group categories

`builderfilter/build.py` resolves these tags to determine which segments to concatenate for each output filter variant.

## Filter Variants

The core `Hiim` set is produced from shared source segments:

| Category | Filters |
|----------|---------|
| Standard | `Hiim` (main balanced filter) |
| Themed | `Hyper`, `TalRasha`, `Vanilla_Plus`, `Mystery` |
| Grail | `Grail` (always shows uniques/sets) |
| Crafting | `Crafting` + 7 class-specific variants |
| LLD | `LLD_Focused`, `LLD_Hyper` |
| Minimal | `Only_Filter`, `Closed_Beta` |

Additional group variants (e.g. `Kassahi`, `Phil777`) are built into `filtergroups/` subdirectories from the same tagged segments.

## Filter Levels (0–11)

Each filter supports 11 strictness levels controlled by in-filter conditions. Higher levels progressively hide lower-value items. Levels 0–2 are permissive (new chars), 9–11 are hyper-strict (mapping/group play).

## Filter Syntax

Output files use Diablo II's native filter language:

```
ItemDisplay[CONDITION]: %DISPLAY_NAME%{TOOLTIP}
```

Color codes, icons, and tooltip blocks are embedded inline. Economy values (rune HR values, currency prices, uber material values) live as `Alias[...]` entries in `builderfilter/02-alias/04-alias-economy-values[ALL].filter` and are referenced by the segments.

**Style-specific icons/sounds in shared segments:** don't inline `%MAP-..%`/`%SOUNDID-..%`/`%DOT-..%` in a shared segment when a style (e.g. the `KassahiStd` bucket) already bakes them into its aliases, and don't make a `[ONLY=...]` copy of the segment. Use an `FX_*` (tags) or `DISP_*` (whole display part) alias from `builderfilter/02-alias/07-alias-site-fx[...]` and give it a value per style; `SITE_FX` is a condition flag for rules only one style wants. Within the Kassahi family, Phil777 vs Kassahi-bucket differences go in same-named aliases: Phil777 values in `02-alias/03-alias-kassahi-luxe`, Kassahi-bucket values in `02-alias/07-alias-site-fx[ONLY=KassahiStd]`; `PHIL777_STYLE` (`TRUE`/`FALSE`) gates rules only one of them uses.

**Shared condition aliases:** use `IN_TOWN` (`builderfilter/01-header/02b-alias-conditions[ALL].filter`) instead of spelling out the town `MAPID` list, and the `SOCK_*` base groups (`builderfilter/02-alias/08-alias-socket-caps[ALL].filter`) for socket-cap lists. A base's socket cap changes in one place there, not in each tooltip copy.

## Economy Data

Two sources keep economy values current:

- **`scripts/update-pd2trader-runes.mjs`** — Node script that pulls median prices from the PD2 Trader API and rewrites the rune / uber-material aliases in `builderfilter/02-alias/04-alias-economy-values[ALL].filter`. Run on a schedule by `.github/workflows/update-pd2trader-rune-values.yml`. Mat values use tiered rounding (`roundMatValue`): nearest 0.01 below 0.25 HR, nearest 0.05 at 0.25 HR and up.
- **Set / unique star tiers** — the source of truth is `builderfilter/data/unique-set-tiers.json`: one entry per unique / set item with `code`, `name`, `base`, `current` and `floor` tiers, an optional `eth` block (`current`/`floor` for ETH copies), and `lld` / `locked` flags. `builderfilter/tier_aliases.py` generates `02-alias/05-unid-unique-set-stars[ALL].filter` from it on every build (a base shows the best tier of any entry on it). Uniques get separate non-ETH (`<tier>_STAR_UNIQUE`, rules use `!ETH`) and ETH (`<tier>_STAR_ETH_UNIQUE`, rules use `ETH`) lists per tier, so any non-ETH / ETH combination works; "ETH copy rated lower" is `ETH 4_STAR_UNIQUE !4_STAR_ETH_UNIQUE` — **edit the JSON, never the alias file**. `scripts/suggest-unique-tiers.mjs` / `suggest-set-tiers.mjs` compare PD2 market listings against it and write suggestions to `temp/` (locked bases skipped, downgrades clamped to floors). `scripts/apply-tier-changes.mjs` writes them back to the JSON: upgrades always, downgrades only with `--downgrades=true` and never below an entry's floor (`scripts/lib/tier-model.mjs` is the shared model). Run every 3 days by `.github/workflows/update-set-unique-tiers.yml`, which opens a `bot/update-set-unique-tiers` PR; set the repo variable `TIER_AUTO_DOWNGRADES` to `true` to include downgrades.
- **`src/Pd2Scraper.java`** — Selenium + JSoup scraper that pulls economy data from pd2.tools and replaces `*_Value` placeholders. Build with `mvn -f mvn.xml` if running locally.

## Filter Validation (Required Step)

**`validate_filters.py` must pass with zero errors before any PR is merged to `main`.**

The validator runs automatically in CI after the build step and will fail the pipeline on any error. It checks all root `.filter` files for:

- Unknown `%TOKEN%` output keywords
- Unmatched tooltip braces `{` / `}`
- Malformed `ItemDisplay[...]` condition brackets
- Invalid condition syntax and out-of-range values

Run it locally at any time:

```bash
python validate_filters.py              # all root *.filter files
python validate_filters.py --errors-only  # suppress warnings
```

Exit code is non-zero if any errors are found, which blocks the CI commit step.

## Development Workflow

1. Edit segment files in `builderfilter/` subdirectories
2. Push to a non-main branch — CI builds filters, runs validation, then commits outputs
3. Fix any errors reported by `validate_filters.py` before opening a PR
4. Open a PR to `main` when ready

## Key Files

- `.github/workflows/build-filters.yml` — full build pipeline
- `version.txt` — auto-incremented build number
- `builderfilter/` — all source filter segments
- `builderfilter/filters.json` — filter definitions, beta flag, and `beta_exclude` (filterdirs that skip beta builds, e.g. `sancofexile`)
- `builderfilter/build.py` — local/CI build script (resolves tags, concatenates segments; regenerates the star-tier aliases)
- `builderfilter/data/unique-set-tiers.json` — unique / set star tiers (current + floor per item); `builderfilter/tier_aliases.py` turns it into the tier aliases
- `validate_filters.py` — filter linter/QA (required to pass)
- `README.md` — user-facing documentation (regenerated by CI from the `builderreadme/` template; edit the template, not the output)
- `builderreadme/create_readme.py` — README generator (template in `builderreadme/README.md`)
- `builderreadme/render_readme_images.py` — preview images for the general Hiim filters (Pillow). The engine in `builderreadme/filterrender/engine.py` evaluates filter rules for sample items in `filterrender/items.py` (unique/set samples come from `unique-set-tiers.json` per star tier); `render_examples.py` draws them
- `scripts/update-pd2trader-runes.mjs` — PD2 Trader economy-value updater (HR rune/mat prices)
- `src/Pd2Scraper.java` — pd2.tools economy data scraper
- `mvn.xml` — Maven POM for the scraper
